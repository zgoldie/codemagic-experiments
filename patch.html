Why 02

Why switch

You already ship OTA with us. Patch is the product we built next: a dedicated dashboard, native fingerprinting, and a CLI that matches how teams actually release.

Dashboard

Releases you can actually run from the UI

Manage apps, promote Staging to Production, and watch downloads, installs, and failures. Team access is RBAC in the dashboard, not a pile of access keys.

Fingerprint

Stop shipping JS to the wrong binary

On every release, the CLI hashes the native project and ties the bundle to a binary version. That pair is what keeps an update off an incompatible build.

CLI

A release command your CI can trust

cmpatch release-react keeps the habit you already have: mandatory, rollout, target binary version. Identity is OAuth, tokens are cm_pat_, not a long-lived access key in a wiki.

What already maps

Apps per platform. Staging and Production. sync() install modes. release-react, mandatory, rollout, target binary version.

// before
import codePush from "@code-push-next/react-native-code-push";
codePush.sync({ installMode: codePush.InstallMode.ON_NEXT_RESTART });

// after
import { sync } from "@codemagic/react-native-patch";
void sync({ installMode: "ON_NEXT_RESTART" });
How 04

How you move

We stand up the hosted Patch server. You swap the client in a native release. Not an over-the-air SDK change.

01

We provision Patch

Same vendor, new service. Apps and deployments can mirror your CodePush layout. You get dashboard login and CLI tokens, not a box to operate.

02

Replace the SDK

Drop the CodePush client. Add @codemagic/react-native-patch. Call sync() from app entry. The Patch client has to ship in a store or internal binary.

03

Point CI at cmpatch

Same release-react shape, new CLI and cm_pat_ tokens. Keep Staging ahead of Production.

04

Cut over

Ship the native build. Publish OTA to that binary. Leave CodePush running until old binaries are gone.
